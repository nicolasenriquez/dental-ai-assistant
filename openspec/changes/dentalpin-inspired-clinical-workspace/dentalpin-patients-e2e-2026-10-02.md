### Final diagnosis, activity and geometry pass

The final pass entered Clinical > Diagnosis and inspected the `Register conditions` card, its chart, the condition tiles, Permanent/Primary selector, collapsible legend and grouped `Diagnosed conditions` list. Permanent showed 32 FDI tooth positions (`18–11`, `21–28`, `48–41`, `31–38`); Primary switched to 20 (`55–51`, `61–65`, `85–81`, `71–75`). Selecting the Caries tile displayed a selected-tool state and the prompt to click a tooth. The tile selection was cancelled before clicking a tooth, so this audit does **not** assert a live save result. The source `DiagnosisMode.vue` composes `OdontogramChart.vue`, `ConditionsList.vue` and the condition/action layer; the backend odontogram module owns tooth/treatment/history reads and writes. These files inform the target interaction, but its new patient-owned condition model is specified separately in `patient-clinical-contract.md`.

The final Activity pass switched among All, Clinical notes and Medical history. All showed a day-grouped timeline with category chips, a vertical connector, icon markers, bordered event cards, timestamp/metadata chips and chevrons to context. The latter two filters showed `No events in this category` and `Show all activity`; All restored the event list. The source `patient_timeline` module stores module-published events. The target will instead project its own approved evolutions, note revisions and tooth-condition revisions, preserving the observed timeline structure and empty/reset behavior without importing finance, communication or appointment event types.

## Verification limits

- The browser fixture was a small demo. Its 15 rows, six debt-filtered rows and two visit events describe only that fixture; they are not acceptance constants.
- No create, edit, archive, upload, clinical note, payment, export or appointment was submitted. Form success/error routes come from source, not live write proof.
- The native browser screenshot API displayed screenshots but did not export a reusable image file in this review. The synthetic structural HTML in `wireframes/` is the portable visual reference; no real identities or clinical text are embedded.
- A Playwright CLI process could not attach to the already authenticated Codex in-app browser. The native browser's Playwright-compatible DOM locators were used for authenticated clicks and field state. This is an automation-surface limitation, not a claim about the app.
